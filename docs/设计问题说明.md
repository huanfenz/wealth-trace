# 设计问题说明（实现过程中发现）

本文档记录在实现《家庭资产管理系统-需求分析与总体设计-V1》时发现的设计问题、冲突或实现风险，
以及每个问题的原因和本项目采用的最简处理方式。

原则：**不擅自改变核心业务模型；只做最小、明确、可解释的处理。**

---

## 1. `transaction` 是 SQL 保留字

**问题**
设计中表名为 `transaction`。SQLite / SQL 标准中 `TRANSACTION` 是保留关键字，
`CREATE TABLE transaction (...)` 会直接语法错误。

**原因**
保留字不能作为未加引号的标识符。

**影响**
建表、查询、索引语句全部会失败。

**最简处理**
保留设计中的表名 `transaction`，但在所有 SQL 中统一加双引号书写为 `"transaction"`。
索引名等不使用该词。这样既不改变业务命名，又能正常建表。

**若可接受的最小改动建议**
把表名改为 `asset_transaction`，可彻底避免加引号。本项目为遵循设计文档，未改名。

---

## 2. 金额精度：设计用 `DECIMAL(20,4)`，技术规范要求整数最小单位

**问题**
设计文档金额字段为 `DECIMAL(20,4)`（4 位小数），而实现技术规范明确要求
「金额使用最小货币单位整数（1 元 = 100 分），全项目统一」。

**原因**
两者对金额精度的约定不同：4 位小数 vs 2 位小数。

**影响**
若按 4 位小数存储，项目出现两套金额语义，违反“全项目统一金额规则”。

**最简处理**
统一采用整数「分」（`INTEGER`，C++ `std::int64_t`，API 也是整数分）。
V1 不管理股票基金份额/净值，2 位小数足够；4 位小数属于未来股票基金净值场景。

**风险与边界**
若 V1 之后要精确到 0.0001 元（如股票基金净值），需要重新评估金额 scale（例如统一到 1e4），
不能局部改动。

---

## 3. 利率表示

**问题**
设计文档利率为 `DECIMAL(10,6)`，技术规范要求定点整数。

**最简处理**
利率统一使用定点整数，`RATE_SCALE = 1000000`（6 位小数）：
`0.018500 → 18500`，与设计文档的 6 位小数一致，无精度损失。

---

## 4. 币种：V1 仅支持人民币，已移除币种字段

**问题**
原设计在 `household`（`base_currency`）、`account`、`asset`、`transaction` 上都带有币种字段，
但 V1 不做汇率换算，统计直接 `SUM(current_balance)`。若同一家庭存在多种币种，
统计结果会把不同币种金额直接相加，属于**错误结果**。

**最简处理**
按需求，V1 **仅支持人民币**，并**彻底移除所有币种字段**：

- 不再有 `household.base_currency`、`account.currency`、`asset.currency`、`transaction.currency`；
- 金额统一为人民币「分」；
- 统计直接求和，结果始终正确。

**影响**
- 数据库 migration、实体、Service、API、前端表单与文档均已同步移除币种；
- 未来若要支持多币种，需要重新引入币种字段与汇率换算，且不能与「直接求和」的统计口径混用。

**说明**
原设计文档中的相关字段已同步标注移除；「多币种自动汇率」仍留在后续扩展清单中。

## 5. 冗余属主字段与账户属主变更

**问题**
账户属主逻辑来源是 `account.owner_member_id`，但 `asset.owner_member_id`、
`transaction.owner_member_id` 冗余保存。若修改账户属主，历史资产/流水会与账户属主不一致。

**原因**
冗余是为了查询简单，但缺少同步机制。

**影响**
成员资产统计会出现“同一个账户的资产分数在两个成员名下”的错乱。

**最简处理**
V1 规定：**账户下已存在资产时，禁止修改账户属主**（返回冲突错误）。
账户没有资产时允许修改。

**不建议**
不要做级联批量更新（会改写历史流水归属，财务上不可接受）。

---

## 6. `opening_balance` 与 `current_balance` 的一致性

**问题**
记账时按 `current_balance = opening_balance + 所有 Transaction 变化` 维护余额；
删除流水并选择保留资产余额时，这一关系可能不再成立。
若在已有交易后修改 `opening_balance`，会破坏该等式。

**最简处理**
- 无任何交易时：允许修改 `opening_balance`，并按差额同步调整 `current_balance`；
- 已有交易后：禁止修改 `opening_balance`（返回冲突错误）。

**建议**
需要修正历史时使用 `ADJUSTMENT`，而不是改初始金额。

---

## 7. 交易时间与 `balance_before` / `balance_after`

**问题**
`transaction_time` 允许用户任意填写（含补记过去时间），而 `balance_before/after`
在写入时按资产“当前余额”计算。

**影响**
若补记一笔较早的交易，之后时间点的历史 `balance_before/after` 不会自动重算，
单看这些冗余字段可能不是“按时间顺序的历史余额”。
通常 `asset.current_balance` 等于 `opening_balance + Σdelta`。若删除流水时选择保留资产余额，
该流水的增量不会再计入公式，但当前余额保持不变，此时两者可能不一致。

**最简处理**
V1 将 `balance_before/after` 视为写入时刻的审计辅助信息（设计文档也是此定位），
不作为历史对账依据。若需要严格历史余额，需要按时间重放，属于后续增强。

## 8. `transaction.status` 取值未定义

**问题**
设计文档有 `status` 字段但未定义枚举值，也没有作废流程。

**最简处理**
定义 `NORMAL` / `VOID`，V1 所有写入为 `NORMAL`；`VOID` 预留，不提供作废 API。

---

## 9. `account.enabled` 的语义未定义

**问题**
设计文档有 `account.enabled`，但未说明禁用账户后的行为。

**最简处理**
V1 中 `enabled` 仅作为展示/管理标记，**不阻止**在该账户下新增资产或交易，
以避免出现“资产仍存在但无法记账”的半失效状态。

**建议**
若未来需要“停用账户禁止记账”，应在 Service 层统一增加校验，并和资产的 `status` 语义一起定义。

## 10. 明细表与资产类型的一致性

**问题**
数据库层面 `asset` 与 `term_deposit_detail/stock_fund_detail/insurance_detail`
是 1:0..1，但未约束“明细类型必须与 asset_type 匹配”，也可为空。

**最简处理**
由 Service 层校验：
- 创建资产时若提供明细块，其类型必须与 `asset_type` 一致，且一次只能提供一个明细块；
- 明细允许为空（对应设计中的 0..1）。

## 11. 跨家庭转账

**问题**
设计文档描述了跨成员转账（同一家庭内），但未明确是否允许跨家庭转账。

**最简处理**
V1 明确**禁止跨家庭转账**（返回参数错误），只允许同一 `household_id` 内的资产互转。
这符合“一次转账是一家人内部资金流动”的直觉，也避免统计口径混乱。

## 12. ER 图中的重复 `account`

**问题**
设计文档第 59/60 节的图中，`household_member` 与 `household` 都指向了一个 `account` 框，
看起来像两条关系。

**最简处理**
以字段定义为准：`account` 同时保存 `household_id` 与 `owner_member_id`，
即“账户属于某家庭 + 属于某成员”。图中重复框视为绘制重复，不额外建表或建关系表。

## 13. `transfer_group_id` 的生成

**问题**
设计文档未规定转账关联 ID 的生成方式。

**最简处理**
在同一写事务内取 `MAX(transfer_group_id)+1` 作为本次转账的组 ID，
两条流水共用，保证一致。V1 为单进程写，配合 `BEGIN IMMEDIATE` 足够安全；
不引入额外的 ID 服务或全局序列。

## 14. 债券基金：独立使用 `BOND_FUND`

**问题**
设计需要同时支持「持有期债基」与「滚动持有债基」。股票基金明细只有锁定期起止日期，
无法表达「每期滚动、下一赎回日随时间推进」。

**最简处理**
新增独立资产类型 `BOND_FUND` 与明细表 `bond_fund_detail`，两类债券基金共用一张表，
用 `holding_mode`（`MIN_HOLDING` / `ROLLING`）区分，**不拆成两个资产类型**。
既有 `FUND` 记录与 `fund_detail` 表通过 migration `008_rename_fund_to_stock_fund.sql`
迁移为 `STOCK_FUND` 与 `stock_fund_detail`，保留原有数据。单独的债券类型由
`009_remove_bond_asset_type.sql` 移除；其资产记录保留并改为 `OTHER`，原 `bond_detail` 专有明细表随之删除。

- 创建时由 Service 计算 `first_redeem_date = purchase_date + holding_period_days`；
- `ROLLING` 型再令 `next_redeem_date = first_redeem_date`；`MIN_HOLDING` 型 `next_redeem_date` 恒为 `NULL`；
- `first_redeem_date` / `next_redeem_date` 允许用户手工修正（节假日顺延、非交易日等），V1 不维护完整交易日历；
- 持有状态（锁定 / 可赎回）不落库，实时按日期推导，避免状态字段与日期字段不一致。

## 15. 业务时区口径（每日维护 / 统计）

**问题**
设计文档的每日维护写的是「每天 00:00」「本地时间 00:00」，但本项目全项目时间统一使用
UTC 字符串（`utils/time_util.hpp`），没有引入本地时区/时区配置。

**最简处理**
引入**统一业务时区**（配置项 `business_timezone`，默认 `Asia/Shanghai`），
所有「业务日期」判断都以它为准，不使用后端 UTC 日期 + 前端浏览器日期混用：

- **审计时间戳**（`created_at` / `updated_at` / `transaction_time`）继续以 UTC 存储，不受影响；
- `time_util::business_today()` 返回业务时区的当前日期；`set_business_timezone()` 在启动、创建线程前调用一次；
- 每日维护以业务日期判定，调度线程等到下一个**业务时区 0 点**执行（`seconds_until_next_business_midnight()`）；
- 债券基金的可赎回状态与剩余天数由**后端**按业务日期计算，随资产 JSON 返回
  （`status` / `days_until_redeem`）；前端只展示，不再用浏览器日期推断；
- `GET /api/meta` 同时返回 `business_timezone` 与 `business_date`。

**统计口径**
统计模块同样改用业务日期：`business_date` 决定「当前自然月」（`overview` 默认年月、
`monthly` 的终点）；月份区间按业务时区边界（首日 00:00:00 ~ 末日 23:59:59）计算，
再经 `time_util::business_to_utc()` 换算成 UTC 区间查询（`transaction_time` 以 UTC 存储）。
`/statistics/period` 的 `from`/`to` 也按业务本地时间解释并换算后查询，返回原样回显。
`monthly` 逐月按各自边界换算，因此即使业务时区存在夏令时也正确。

**说明**
`Asia/Shanghai` 无夏令时，跨时区规则由系统 tzdata 提供。
仅审计时间戳（`created_at` / `updated_at` / `transaction_time`）仍以 UTC 存储，这是刻意为之：
存储用 UTC、展示与统计用业务时区。

## 16. 每日维护的幂等、事务与补跑

**最简处理**
- 任务设计为「收敛到今天应有的状态」，而非逐日回放：`while (today > next_redeem_date) next += period`，
  因此中间缺跑多天只需启动时补跑一次。
- 判断必须用 `today > next_redeem_date`，**不能用 `>=`**：`today == next_redeem_date` 当天仍是有效赎回日，
  若用 `>=` 会在 0 点直接滚入下一期，用户看不到「今日可赎回」。
- 整个任务在一个事务内完成，成功后写入 `system_state.daily_maintenance_last_run`；
  失败则回滚且不更新 `last_run`，下次启动/调度可重跑，天然幂等。
- 程序启动时检查 `last_run` 是否为业务日期今天，不是则立即补跑；运行中再等到下一个业务时区 0 点执行。

## 17. 定期存款每日维护（自动续存）

**问题**
定期存款有「存期」概念（3 个月 / 1 年 / 3 年等），到期日需要按自然月 / 自然年计算；
开启自动续存后，到期当天应进入下一存期，且停机多天也要能一次推进到正确周期。

**最简处理**
- **到期日计算**：`maturity_date = add_term(start_date, term_value, term_unit)`，
  支持 `DAY / MONTH / YEAR`；目标月不存在对应日时落到该月最后一天
  （`2026-01-31 + 1 MONTH = 2026-02-28`，`2024-02-29 + 1 YEAR = 2025-02-28`）。
  统一实现在 `utils/term_date.hpp`，避免各处自行实现。允许用户手工修正 `maturity_date`。
- **必填校验**：Service 层要求 `start_date` / `term_value(>0)` / `term_unit` 必填；
  缺少 `maturity_date` 时自动计算。
  > 数据库列仍保持可空（沿用 `001_init.sql`），不在 migration 中改 NOT NULL，
  > 以免破坏既有数据；由 Service 层强制约束。
- **每日维护**（`DailyAssetMaintenanceService::update_term_deposits`）：
  - `auto_rollover = 0`：不修改任何日期，`maturity_date` 保持不变；
  - `auto_rollover = 1`：`while (today >= maturity_date)` → `start_date = maturity_date`，
    `maturity_date = add_term(maturity_date, term_value, term_unit)`，直到 `maturity_date > today`；
  - `start_date` 始终表示「当前存期起始日」，自动续存后同步推进；不新增 `original_start_date`。
- **`today >= maturity_date`（与滚动债基的 `today > next_redeem_date` 不同）**：
  自动续存产品到期当天新一期已经开始，故当天即推进；滚动债基当天仍是赎回窗口，故不推进。
- **不自动修改**：`asset.opening_balance`（本金）/ `asset.current_balance` /
  `annual_interest_rate` / 交易流水。
  续存利率可能与上一期不同，V1 保留原利率，由用户确认（后续可加 `rate_needs_confirmation`）。
- **到期状态不落库**：由 API 按业务日期实时推导
  （`today < maturity` → `ACTIVE`；`today >= maturity` 且不自动续存 → `MATURED`），
  随 `term_deposit` JSON 返回 `status` / `days_until_maturity`。
- 自动续存与债券基金共用 `system_state.daily_maintenance_last_run`、同一事务与补跑机制，
  且天然幂等（推进后当天再执行时 `today < maturity_date`，不再变化）。

**V1 边界**
每日任务只推进日期与推导状态；真实到账、利息、本金变化一律由用户业务操作维护。

## 18. 去重：明细不再保存本金与名称

**问题**
明细表里的 `principal` 与资产 `opening_balance` 语义重复；
`fund_name` / `bond_name` 与资产 `asset.name` 重复。同一含义在两处保存容易不一致。

**最简处理**
历史 migration `004_remove_redundant_fields.sql` 当时删除以下重复列；单独债券类型及其表后来由 migration 009 移除：

- 本金：`term_deposit_detail.principal`、`bond_detail.principal`、`bond_fund_detail.principal`；
- 名称：资产名称统一保存在 `asset.name`，扩展明细不重复存储名称。

统一口径：**本金一律以 `asset.opening_balance` 为准，名称一律以 `asset.name` 为准**。
实体、仓储、DTO、控制器与前端类型 / 表单同步去掉这些字段，API 请求与响应不再包含它们
（`principal` / `fund_name` / `bond_name`）。每日维护不涉及这些字段，不受影响。

**实现说明**
使用 SQLite 3.35+ 的 `ALTER TABLE ... DROP COLUMN` 删除；被删列均非主键、未被索引、
未被外键引用。已在含数据的库上验证升级后其余字段与数据完整保留。

## 19. 维护时机：添加时维护与手动维护

**问题**
每日维护只在启动补跑与每天 0 点调度时执行。若用户新增一个「购买日期较早」的滚动持有债基，
或新增一个早已到期的自动续存定存，系统会先按原始日期落库，列表立即显示 `PENDING` /
过期周期，要等到下次维护才收敛，体验突兀；用户也可能希望随时手动重跑维护。

**最简处理**
在保留既有两个自动时机的前提下，新增「添加时维护」与「手动维护」，三者共用同一套推进规则
（抽到 `utils/maintenance_rules.hpp` 的纯函数，供每日维护、创建时维护与预览复用，避免口径分叉）：

- **添加时维护**：新增资产可传 `maintain_on_create=true`，服务端在写入前把过期的
  `next_redeem_date`（滚动债基）或本期起止日期（自动续存定存）推进到当前周期。
  为避免「悄悄改日期」，前端先调 `POST /api/households/{id}/assets/maintenance-preview`
  预览推进前后值，弹框经用户确认后再带该标记提交；用户取消则放弃本次新增。
- **手动维护**：`GET /api/maintenance/preview` 预览全局将产生的变更，
  `POST /api/maintenance/run` 强制执行一次（`run()` 幂等，返回各类推进条数）。
  资产页「手动维护」按钮先预览、确认后执行。
- 预览与执行都走 `time_util::business_today()` 的业务日期口径，规则与每日维护完全一致：
  滚动债基 `today > next_redeem_date` 才推进，自动续存定存 `today >= maturity_date` 即续期。
- 手动 `run()` 会更新 `daily_maintenance_last_run`，但因任务幂等，不影响当天后续的零点调度。
