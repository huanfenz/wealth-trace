# 设计问题说明（实现过程中发现）

本文档记录在实现《家庭资产管理系统-需求分析与总体设计-V1》时发现的设计问题、冲突或实现风险，
以及每个问题的原因和本项目采用的最简处理方式。

原则：**不擅自改变核心业务模型；只做最小、明确、可解释的处理。**

---

## 1. `transaction` 是 SQL 保留字

**问题**
设计中表名为 `transaction`。SQLite / SQL 标准中 `TRANSACTION` 是保留关键字，
`CREATE TABLE transaction (...)` 会直接语法错误。

**原因**
保留字不能作为未加引号的标识符。

**影响**
建表、查询、索引语句全部会失败。

**最简处理**
保留设计中的表名 `transaction`，但在所有 SQL 中统一加双引号书写为 `"transaction"`。
索引名等不使用该词。这样既不改变业务命名，又能正常建表。

**若可接受的最小改动建议**
把表名改为 `asset_transaction`，可彻底避免加引号。本项目为遵循设计文档，未改名。

---

## 2. 金额精度：设计用 `DECIMAL(20,4)`，技术规范要求整数最小单位

**问题**
设计文档金额字段为 `DECIMAL(20,4)`（4 位小数），而实现技术规范明确要求
「金额使用最小货币单位整数（1 元 = 100 分），全项目统一」。

**原因**
两者对金额精度的约定不同：4 位小数 vs 2 位小数。

**影响**
若按 4 位小数存储，项目出现两套金额语义，违反“全项目统一金额规则”。

**最简处理**
统一采用整数「分」（`INTEGER`，C++ `std::int64_t`，API 也是整数分）。
V1 不管理基金份额/净值，2 位小数足够；4 位小数属于未来基金净值场景。

**风险与边界**
若 V1 之后要精确到 0.0001 元（如基金净值），需要重新评估金额 scale（例如统一到 1e4），
不能局部改动。

---

## 3. 利率表示

**问题**
设计文档利率为 `DECIMAL(10,6)`，技术规范要求定点整数。

**最简处理**
利率统一使用定点整数，`RATE_SCALE = 1000000`（6 位小数）：
`0.018500 → 18500`，与设计文档的 6 位小数一致，无精度损失。

---

## 4. 币种：V1 仅支持人民币，已移除币种字段

**问题**
原设计在 `household`（`base_currency`）、`account`、`asset`、`transaction` 上都带有币种字段，
但 V1 不做汇率换算，统计直接 `SUM(current_balance)`。若同一家庭存在多种币种，
统计结果会把不同币种金额直接相加，属于**错误结果**。

**最简处理**
按需求，V1 **仅支持人民币**，并**彻底移除所有币种字段**：

- 不再有 `household.base_currency`、`account.currency`、`asset.currency`、`transaction.currency`；
- 金额统一为人民币「分」；
- 统计直接求和，结果始终正确。

**影响**
- 数据库 migration、实体、Service、API、前端表单与文档均已同步移除币种；
- 未来若要支持多币种，需要重新引入币种字段与汇率换算，且不能与「直接求和」的统计口径混用。

**说明**
原设计文档中的相关字段已同步标注移除；「多币种自动汇率」仍留在后续扩展清单中。

## 5. 冗余属主字段与账户属主变更

**问题**
账户属主逻辑来源是 `account.owner_member_id`，但 `asset.owner_member_id`、
`transaction.owner_member_id` 冗余保存。若修改账户属主，历史资产/流水会与账户属主不一致。

**原因**
冗余是为了查询简单，但缺少同步机制。

**影响**
成员资产统计会出现“同一个账户的资产分数在两个成员名下”的错乱。

**最简处理**
V1 规定：**账户下已存在资产时，禁止修改账户属主**（返回冲突错误）。
账户没有资产时允许修改。

**不建议**
不要做级联批量更新（会改写历史流水归属，财务上不可接受）。

---

## 6. `opening_balance` 与 `current_balance` 的一致性

**问题**
设计规定 `current_balance = opening_balance + 所有 Transaction 变化`。
若在已有交易后修改 `opening_balance`，会破坏该等式。

**最简处理**
- 无任何交易时：允许修改 `opening_balance`，并按差额同步调整 `current_balance`；
- 已有交易后：禁止修改 `opening_balance`（返回冲突错误）。

**建议**
需要修正历史时使用 `ADJUSTMENT`，而不是改初始金额。

---

## 7. 交易时间与 `balance_before` / `balance_after`

**问题**
`transaction_time` 允许用户任意填写（含补记过去时间），而 `balance_before/after`
在写入时按资产“当前余额”计算。

**影响**
若补记一笔较早的交易，之后时间点的历史 `balance_before/after` 不会自动重算，
单看这些冗余字段可能不是“按时间顺序的历史余额”。
但 `asset.current_balance` 始终等于 `opening_balance + Σdelta`，**总额始终正确**。

**最简处理**
V1 将 `balance_before/after` 视为写入时刻的审计辅助信息（设计文档也是此定位），
不作为历史对账依据。若需要严格历史余额，需要按时间重放，属于后续增强。

---

## 8. `transaction.status` 取值未定义

**问题**
设计文档有 `status` 字段但未定义枚举值，也没有作废流程。

**最简处理**
定义 `NORMAL` / `VOID`，V1 所有写入为 `NORMAL`；`VOID` 预留，不提供作废 API。

---

## 9. `account.enabled` 的语义未定义

**问题**
设计文档有 `account.enabled`，但未说明禁用账户后的行为。

**最简处理**
V1 中 `enabled` 仅作为展示/管理标记，**不阻止**在该账户下新增资产或交易，
以避免出现“资产仍存在但无法记账”的半失效状态。

**建议**
若未来需要“停用账户禁止记账”，应在 Service 层统一增加校验，并和资产的 `status` 语义一起定义。

---

## 10. 明细表与资产类型的一致性

**问题**
数据库层面 `asset` 与 `term_deposit_detail/fund_detail/bond_detail/insurance_detail`
是 1:0..1，但未约束“明细类型必须与 asset_type 匹配”，也可为空。

**最简处理**
由 Service 层校验：
- 创建资产时若提供明细块，其类型必须与 `asset_type` 一致，且一次只能提供一个明细块；
- 明细允许为空（对应设计中的 0..1）。

---

## 11. 跨家庭转账

**问题**
设计文档描述了跨成员转账（同一家庭内），但未明确是否允许跨家庭转账。

**最简处理**
V1 明确**禁止跨家庭转账**（返回参数错误），只允许同一 `household_id` 内的资产互转。
这符合“一次转账是一家人内部资金流动”的直觉，也避免统计口径混乱。

---

## 12. ER 图中的重复 `account`

**问题**
设计文档第 59/60 节的图中，`household_member` 与 `household` 都指向了一个 `account` 框，
看起来像两条关系。

**最简处理**
以字段定义为准：`account` 同时保存 `household_id` 与 `owner_member_id`，
即“账户属于某家庭 + 属于某成员”。图中重复框视为绘制重复，不额外建表或建关系表。

---

## 13. `transfer_group_id` 的生成

**问题**
设计文档未规定转账关联 ID 的生成方式。

**最简处理**
在同一写事务内取 `MAX(transfer_group_id)+1` 作为本次转账的组 ID，
两条流水共用，保证一致。V1 为单进程写，配合 `BEGIN IMMEDIATE` 足够安全；
不引入额外的 ID 服务或全局序列。
